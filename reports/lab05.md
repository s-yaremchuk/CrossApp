# Лабораторна 5 — сервісний шар бібліотеки

## Мета та хід роботи

Мета — виконати однакові операції видачі й повернення з двома способами зберігання. Одиниця обліку — фізичний примірник BookCopy. Він має інвентарний номер, опис видання BookDto та ознаку видачі IsIssued. ISBN може повторюватися у двох примірників одного видання.

### 1. Контракт сховища

| Метод IBookStore | Для чого потрібен |
| --- | --- |
| List() | Показати поточний каталог. Повертає знімок колекції. |
| GetById(id) | Знайти примірник за інвентарним номером. Для відсутнього номера повертає null. |
| Add(copy) | Додати примірник. Повторний номер викликає InvalidOperationException. |
| Update(copy) | Зберегти змінений стан після видачі або повернення. |
| Remove(id) | Вилучити запис. Результат false означає, що такого номера немає. |

### 2. Дві реалізації та сервіс

InMemoryBookStore зберігає знімки у словнику. Ключі порівнюються без урахування регістру. SampleData створює 16 примірників восьми видань. Наступний запуск знову починається з цього набору.

FileBookStore завантажує JSON під час першого звернення і тримає каталог у пам’яті. Після Add, Update або успішного Remove сховище записує масив BookCopyDto. Кожен елемент містить Id, вкладене видання Book та IsIssued. Тимчасовий файл замінює попередній лише після успішного запису. Шлях для стандартної збірки Debug наведено в плані захисту.

Схема залежностей: Cli → LendingService → IBookStore. Контракт реалізують InMemoryBookStore і FileBookStore. Сервіс створює примірник, викликає його доменні методи Issue та Return і передає змінений стан у сховище через Update.

### 3. Ручне підключення і додаткові завдання

У Program.cs фабрика вибирає сховище й за потреби додає кеш. Точка входу передає отриманий об’єкт у конструктор LendingService. Обидва режими виконують один каталоговий сценарій.

~~~csharp
internal static IBookStore Create(string[] args)
{
    IBookStore store = args.Contains("--file")
        ? new FileBookStore(DataPath)
        : new InMemoryBookStore(SampleData.Copies());
    return args.Contains("--cache") ? new CachingBookStore(store) : store;
}
~~~

Фабрика. StoreFactory.Create(args) зосереджує вибір та обгортання сховища в одному методі. При прямому підключенні ці самі умови довелося б розмістити серед команд запуску. Для обох варіантів конструктор сервісу однаковий.

Декоратор. CachingBookStore приймає IBookStore. Перший GetById читає запис із внутрішнього сховища. Повторне читання використовує кеш. Після зміни відповідний ключ видаляється з кешу. Тому після повернення Find показує актуальне значення False.

Пошук. LendingService.Search приймає Func<BookCopy, bool>. Сценарій передає item => item.IsIssued і після видачі знаходить один примірник на початковому наборі.

### 4. Результати запуску

| Режим | До додавання | Усього після запуску |
| --- | --- | --- |
| InMemoryBookStore, запуск 1 і запуск 2 | 16 у кожному | 17 у кожному |
| FileBookStore, запуск 1 зі свіжим файлом | 0 | 1 |
| FileBookStore, запуск 2 | 1 | 2 |

### Висновок і питання

Що дає ручний DI? Cli вибирає сховище і передає його через конструктор. Як перевірити сервіс без диска? Передати InMemoryBookStore. Що зміниться на тижні 11? Потрібні реалізація IBookStore для бази даних, відображення полів і вибір реалізації у фабриці. Контракт та бізнес-операції сервісу залишаються придатними для обох джерел.
